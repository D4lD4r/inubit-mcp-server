- [major] FR-007 / FR-018 / US4 – Contradiction on `restore_backup` of a **deployment** backup: today (docs/tools.md, `restore_backup`, feature 005) such a backup is restored on its node of the target group – even if that node is not a development stage – including repository files. FR-018 puts every `restore_backup` of repository files "under the same switch check (FR-004)", and FR-003 forbids `repository: write` on non-development nodes, so FR-018 read literally would refuse every deployment-backup restore that touches repository files – a regression of 005 that FR-007 says must not happen. – Proposed wording for FR-018: "The switch check and the always-required confirmation apply to restoring backups of development calls (`import_artifacts`, `restore_backup`) only; restoring a `deploy_release` backup keeps the behaviour of feature 005 regardless of the switch." Add an acceptance scenario for it.
- [major] FR-002 vs FR-003 – FR-002 allows `repository: write` in `defaults`, but FR-003 makes an effective `write` on any node that is not a development stage a startup error. Since every non-development node (int, prod and every other stage – not only production groups, unlike `e2eTests`, which ConfigValidator only rejects on production) inherits from `defaults`, `write` in `defaults` would be a startup error in almost every real profile. – Decide and state one of: (a) `repository` is not allowed in `defaults` (or on groups containing non-development nodes); (b) an inherited `write` on a non-development node is silently treated as `read-only`, only an explicit node/group value there is an error; (c) keep, and document that `defaults: write` only works when every node is a development stage. Story 2 scenario 3 should then name inherited vs. explicit placement.
- [major] FR-010 / FR-011 – The spec does not define what a **module import** (`modules` scope of feature 004) does when the modules reference new or changed repository files. FR-011 covers only diagram-group imports. If such files go to `notImported`, the modules land on the node bound to the old schema/stylesheet; if they are included, FR-004/FR-012 must apply. – Question: "Does a module import include the new and changed repository files its modules reference (transitively, as in FR-011), refuse, or list them in `notImported`?" Add an acceptance scenario.
- [major] FR-011 – "the group's workflows' modules" is ambiguous: all modules of the diagram group, or only the modules of the workflows/modules in the change set? Also open: is a diagram-group import with **only** changed repository files (no changed workflow) valid, and what does it send (and tag, if `tag` is given)? – Proposed wording: "…the new and changed repository files referenced by any module of the diagram group in the workspace (changed or not)…" and "A diagram-group import whose change set contains only repository files imports them [and tags the group if requested] / is refused with …".
- [major] FR-012 / FR-015 / US1 – The mandatory `reason` is not addressed for repository files. Feature 004 (FR-017) requires the reason in the check-in comment of every new version and its import verification checks it; the spec does not say whether INUBIT's repository import mode carries a version comment, whether verification checks it, or whether the reason is only audited for repository files. – Question: "Does the reason appear in the version comment of each imported repository file and is it part of the verification? If INUBIT cannot carry it, state that it is recorded only in the audit and the workspace history."
- [minor] FR-001 – "Writing to the INUBIT repository of a node MUST be disabled unless…" read literally also forbids `deploy_release` repository writes, contradicting FR-007. – Wording: "Writing to the INUBIT repository of a node **through the development tools** MUST be disabled unless…"
- [minor] FR-013 – "since its last export from that node" differs from the feature 004 base (last verified server state: export **or** development call); after a successful import the last export is older than the imported state. Also unclear whether a changed description/content type on the node with identical content counts as a conflict. – Wording: "…changed on the node since its last verified state in the workspace history (export or development call); only content counts, not [version, check-in comment, description]."
- [minor] FR-018 – Feature 004 FR-019 requires the conflict check (against the state the referenced call left) on restore; FR-018 only mentions verification for repository files. – Add "…with the conflict check against the state the referenced call left and rollback on failure."
- [minor] FR-015 / US4 – "byte for byte" may fail spuriously if INUBIT's repository import normalizes line ends, trailing newline, encoding or BOM (feature 004 already tolerates such normalizations for embedded stylesheets/WSDLs). – Question: "Is verification strictly byte-identical, or byte-identical after the normalizations documented for embedded documents?"
