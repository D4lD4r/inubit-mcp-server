SPEC: specs/025-inubit-74-support/spec.md  ROUND: 1
FINDINGS:
- [major] US2 / FR-005 / FR-032 / FR-016 – Both the 7.4 hint (IMC-6 criterion 1) and Mandate B detection fire only when the detection request (`system/info`, see `VersionGate.unknown` and `DetectionFailure.endpointMissing`) gets HTTP 404. The spec never says that a 7.4 node actually answers 404. Unlike 6.1, 7.4 has a REST API from before 8.0, so it could answer 401, 200 with XML/HTML (UNEXPECTED_RESPONSE), or even a parsable version. Then the hint never appears and FR-032 never triggers. FR-016 and US4 scenario 1 also forbid any REST case, so Mandate B can never check this premise. – Question: what does a 7.4 node answer to the detection request? Proposed wording: (a) add an Assumption like the one in feature 012: "A 7.4 node answers the detection request with HTTP 404; if it answers otherwise, the hint of FR-005 does not appear and the warning stays as today." (b) Either add one read-only recorder case `v74_rest_detection` (the detection request only; status line and scrubbed body; the only REST request in the catalogue; US4 scenario 1 adjusted), or state that FR-032's trigger is decided from the Mandate B recordings and is not fixed to 404.
- [major] Scope / IMC-6 criterion 3 / FR-007 – FR-006 to FR-013 protect only nodes known as 7.4 (pinned). A real 7.4 node on `AUTO` stays "unknown". Today that means reads run with the 8.1 REST adapters and the "results are unverified" warning (`VersionGate.judge`, lines 391-396). In Mandate A this is always the case, in Mandate B whenever detection fails. Read literally, IMC-6 criterion 3 ("No tool sends a request whose shape is unverified") is broken. FR-020 keeps the behaviour implicitly, but no section says so. – Question: is this accepted? If yes, add an Edge Case or Out-of-Scope line: "A 7.4 node on `AUTO` that is not identified as 7.4 is handled as an unknown version exactly as today (reads with the 8.1 adapters and the 'unverified' warning, writes refused); criterion 3 applies to nodes known as 7.4. The setup docs tell 7.4 operators to pin `V7_4`." If no, specify what changes for unknown nodes after a 404 (for example reads refused instead of warned), and accept the regression for 6.1/8.1 in FR-020.
- [major] FR-017 / FR-029 – FR-017 applies "the TLS arguments ... of feature 013 unchanged" to the 7.4 recorder. `tools/record-fixtures.ps1` passes `--trustStoreFilePath` and `--disableHostNameVerification` (lines 271-276), and the attached 7.4 help lists neither option, so an HTTPS recording would break or behave unpredictably. FR-029 cites only the server-side pin check (012 FR-012). It does not cite 012 FR-012a, which is the rule that matters for a client without these options: trust store through the client's Java runtime, `disableHostnameVerification: true` refused with `TLS_ERROR`, fail closed. – Proposed wording: FR-017: "For 7.4 cases the recorder MUST NOT pass `-TrustStore` / `-DisableHostNameVerification` as client options; an HTTPS 7.4 node is recorded with the trust store given to the client's Java runtime [state how], or the recorder stops." FR-029: "... feature 012 FR-012 and FR-012a apply; the 7.4 client counts as having neither a trust-store nor a host-name option until the recordings show otherwise."
- [major] FR-014 / FR-015 / FR-016 / FR-030 – FR-014 does not list the reconstructed 7.4 cases or map them to the recorder cases, and the names differ (recorder `v74_help` vs fixture `help`). The 6.1 precedent (`fixtures/v6_1/cli/RECONSTRUCTED.txt`) contains `health_session_de`, `health_session_alive_failed`, `health_session_maintenance`, `login_failed`, `unreachable`, `ps_session_empty`, `ps_session_unassigned`, `ps_session_de`. FR-016 records none of German output, a negative alive check, maintenance on (would need a write), a failed login, an empty listing or the Processing state. FR-030 blocks `supported` while any case is still reconstructed. So Mandate B is either blocked forever, or the planner deletes those cases and the tests for US6 scenario 2, US7 scenario 4 and FR-025 lose their coverage. – Questions/wording: (a) Add a table "7.4 fixture case | capability | recorder case that replaces it". (b) Add recorder cases that can be produced read-only on a healthy node: `v74_login_failed` (wrong password), `v74_ps_processing`, an empty-filter listing, and German output if the client locale can be switched. (c) For cases that cannot be recorded read-only on a non-production node (alive negative, maintenance on), decide whether they may be derived from a recording by a documented, minimal edit and listed separately (e.g. `DERIVED.txt`, allowed by the guard), or whether those scenarios are dropped for 7.4.
- [major] Mandate A / FR-001 / FR-010 – The spec does not say what a configured `defaults.cliClients."7.4"` entry does in Mandate A. Feature 017 FR-006 makes `--check-config` run every configured client locally (`startcli -v`), and FR-015 shows the client directory per node in `list_nodes` / `--check-config`. Open points: (1) Does `--check-config` run the unverified 7.4 client (output format unknown, so the range check is NOT_EVALUABLE)? (2) Is there a JDK major warning for 7.4? The Assumptions say Java 11 or older, but 017 FR-006 warns only for 8.1/9.0. (3) What does `list_nodes` show as the client of a 7.4 node? – Proposed wording, new FR: "In Mandate A a `"7.4"` entry is validated syntactically and its directories checked for existence; `--check-config` [does / does not] run its local version probe and [does not] warn on its JDK; `list_nodes` shows the client directory per 017 FR-015 with the note that no tool uses it until 7.4 is verified."
- [major] FR-029 / FR-032 / Edge Case "8.1 cliHome" – FR-029 ("no other client MUST be used against a 7.4 node") overrides feature 017 FR-003 precedence (node `cli.home` → group `cli.home` → version entry → `defaults.cliHome`) without saying so. A node-level `cli.home` that points at a real 7.4 client would be ignored. FR-032 runs the 7.4 client against a node of unknown version, which contradicts 017 FR-005 ("version unknown → version-less client") and FR-029's own premise. It can also reach a 6.1 node, or an 8.1 node behind a proxy that answers 404, so FR-033's guarantee "no additional request reaches an 8.1 or 9.0 node" cannot be checked. – Questions: (a) For 7.4 nodes, does node/group `cli.home` still win (accepted when its `-v` shows a 7.4 client) or only `cliClients."7.4"`? Write the chosen precedence into FR-029 as an explicit deviation from 017 FR-003. (b) For FR-032: name the exception to 017 FR-005, say whether the TLS checks of 012 FR-012/012a run before the detection StartCLI run, and reword FR-033 to "no additional REST request reaches a node that answers the detection request successfully; a node whose detection fails with 404 may receive one StartCLI version run of the 7.4 client".
- [minor] Mandates – Planning could pick up Mandate B work (parsers, detection) whose inputs do not exist yet. – Proposed wording under "Mandates": "plan.md and tasks.md for this round cover Mandate A only; Mandate B is re-clarified from the recordings before it is planned."
- [minor] FR-007 / US1 scenario 3 – "a next step" is not defined for 7.4, where no pin helps. – Proposed: name the text, e.g. "INUBIT 7.4 is recognised but no tool is verified on it yet; use the INUBIT Workbench for <capability> on <node>."
- [minor] US1 scenario 3 ("any write") – The order of refusals is not stated: when writes are disabled for the environment, does a write on a 7.4 node get the write-gate refusal or `UNSUPPORTED_VERSION`? – State the order (as for 6.1).
- [minor] FR-003 / US3 – Cases not covered: two three-part 7.4 values ("7.4.0" vs "7.4.0") and a patch difference with the fourth part absent on one side ("7.4.0" vs "7.4.1.5"). FR-003 makes both "not comparable" or leaves them open. – Proposed: "compare major.minor.patch first; a difference there is a mismatch; only when they are equal does a fourth part present on one side only make the result not comparable; both absent and equal is a match."
- [minor] FR-018 – Only the session commands are editable in the catalogue. The direct options of `v74_direct_health` (several in one run, unverified) and the end-of-session command of FR-017 (not in the help) may also need changes on site. – Extend FR-018 to "the arguments and commands of every 7.4 case, including the end-of-session command".
- [minor] FR-028 – "the fields the recordings show (at least process id, workflow, state and time)" contradicts itself if a recording lacks time. The "hanging" rule in US7 has no threshold. – Proposed: "the fields of the 6.1 result shape that the recordings provide; process id, workflow and state are required, otherwise UNEXPECTED_RESPONSE; hanging per the 6.1 rule of feature 012 when time in state is present."
- [minor] Mandate B documentation – FR-020 covers the docs for Mandate A only. The constitution (Workflow: docs in the same change) also requires the setup and tool reference for 7.4 health/processes and `cliClients."7.4"`. – Add to FR-031 or a new FR: "user docs and changelog updated when a 7.4 capability is declared supported."
- [minor] Constitution V / Preconditions – Mandate A declares 7.4 "StartCLI only" in the production matrix. The Principle V exception is worded for "a version whose REST interface does not offer what the server needs"; for 7.4 the REST interface is unverified, not missing. – Have the planned amendment cover "REST unverified" as a reason, or state in the Context that an all-unsupported CLI-only entry does not invoke the exception.
- [minor] What vs how – Class and test names (`InubitVersion`, `V61RecordedFixturesTest`), file layout (`RECONSTRUCTED.txt`, `.stdout/.stderr/.exit`) and FR-019 (git line-end handling) are plan-level. This is acceptable as repo convention (precedents 012/017 do the same), but FR-019 could read "Windows recordings are stored byte-exact" and leave the mechanism to the plan.
