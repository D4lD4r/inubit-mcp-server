- [major] FR-012 / US5-3 / Context "client's own trust-store and host-name options" – Host-name verification is specified only for the server's own handshake. StartCLI makes its own HTTPS connection; today the server skips host names there via `--disableHostNameVerification` (CliRunner), which the 6.1 client does not document. A 6.1 client's runtime will check the host name and fail, so US5-3 ("the host name is not checked and the pin is") is unattainable with a 6.1 client (only with the 8.1.17 client, if it works against 6.1). – Question: What happens for a 6.1 node with `disableHostnameVerification: true` + pin whose client cannot skip host-name verification? Proposed wording: "If the node's StartCLI client offers no way to skip host-name verification, a 6.1 node with `disableHostnameVerification: true` MUST be reported by `--check-config` and at startup as a configuration error (or: StartCLI-backed tools on it MUST fail with `TLS_ERROR` naming the missing client option). Host-name verification of the client MUST NOT be disabled by any other means." Add a US5 scenario for this case.
- [major] FR-012 "by the trust-store settings of its Java runtime" / Constitution II – Handing a trust store to the client's JVM means system properties in a process argument or an environment variable (e.g. `JAVA_TOOL_OPTIONS`, which CliRunner already sets). The configuration supports a password-protected trust store (`credentials.parameters.trustStorePassword`); its password would then appear on a command line or in the environment, which Constitution II forbids, and FR-011 only covers the login password. Also, a Java 7 runtime (6.1 before patch 6.1.0.89) cannot read PKCS12 trust stores with trusted-certificate entries (today's format). – Questions: (a) May a trust-store password ever reach the 6.1 client, and how? Proposed wording: "A trust-store password MUST NOT appear in any argument or environment variable of the client process; if the node's client can only receive the trust store through its runtime's settings, a password-protected trust store MUST be refused for that node by `--check-config` and at startup, with the next step 'use a password-less trust store'." (b) Which trust-store formats must work with a 6.1 client's runtime — or left to the plan with a `--check-config` finding when format and runtime do not fit?
- [major] FR-014 / FR-012 – FR-014 says the TLS check uses the host from `baseUrl`, but `cli.url` can be overridden per node/group (ConfigValidator only checks it when it differs from `baseUrl` + `/ibis/servlet/IBISSoapServlet`). Then the server's pin check verifies a different endpoint (host, port, even scheme) than StartCLI connects to, and the pin protects nothing; "an HTTPS 6.1 node" in FR-012 is ambiguous when `baseUrl` and `cli.url` differ in scheme. – Proposed wording: "For a 6.1 node, the TLS check of FR-012 MUST target the host and port of the effective StartCLI URL; a node is 'HTTPS' when its effective StartCLI URL uses https://." (Alternative: a 6.1 node whose `cli.url` differs in scheme, host or port from `baseUrl` is a configuration error.)
