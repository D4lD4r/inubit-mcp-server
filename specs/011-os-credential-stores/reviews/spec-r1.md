SPEC: specs/011-os-credential-stores/spec.md  ROUND: 1

No `[NEEDS CLARIFICATION]` markers left; no conflict with the constitution (Principle II lists an OS/secret store as an allowed source, so dropping environment variables is a narrowing). I checked the Context & Findings against the code and docs: `CredentialResolver`/`CredentialVariables` (naming, normalisation, node before group by value, unmatched-`_PASSWORD` warning), `SecretPlan` (node → group → profile → environment), `SecretLabels` (the "restart the MCP client from a shell" next step), `ConfigValidator` (startup checks that read variable values), `ConfigSummary` (`Credential variables:` line), `NodeSecrets` (10 s timeout, 30 s back-off), `Launcher`/`Wiring` (`System.getenv()`), `LiveTarget` (profile prefix only, no plans), `Format001Detector`, `docs/setup.md` section 4, `docs/tools.md`, `README.md`, `CHANGELOG.md` (Unreleased E2E fix; current version 0.6.2). All Context claims hold. The open points are below: the entry identity on Windows, error codes, startup checks that today depend on variable values, the access-dialog behaviour, and the new prefix key.

FINDINGS:
- [major] FR-004 / Clarification Q4 / US2 AS1 / SC-007 – The Windows Credential Manager has no service/account pair. A generic credential has one `TargetName` plus a `UserName` field. FR-004 leaves the mapping to "the documentation", but users have to create entries under that name, so it is product behaviour and must be testable. The Linux attributes are fixed (`service`, `account`); the Windows mapping is not. – Fix the Windows identity in the spec, e.g. "target name `inubit-mcp:<ACCOUNT>`, the user-name field is ignored (or must equal `<ACCOUNT>`)". If the decision stays with the plan, say so explicitly and add an acceptance scenario that uses the exact name the docs prescribe.
- [major] Edge Cases / FR-007 – Value encoding is not defined. Windows tools usually store the secret blob as UTF-16LE. Keychain and Secret Service store bytes, and tools that read the value from stdin may keep a trailing newline. If the server decodes differently from the tool the docs prescribe, the login is rejected and the node is paused for 60 s, with no hint. – Add a requirement: "A value created with the documented system tool of each OS is read exactly as typed (character encoding as that tool writes it; no trailing line break added or kept)". Also state what a value that cannot be decoded is ("invalid value").
- [major] FR-010 / US1 AS3–4 / US2 AS3 – The error code of each failure kind is not stated. Only "not found" is tied to `AUTH_FAILED` (US1 AS3). Feature 010 maps "someone must fix it" to `AUTH_FAILED` and "cannot be reached / timeout" to `UNREACHABLE` (docs/setup.md, "First use, timeout and back-off"). – State the code per kind: not found, invalid value and access denied → `AUTH_FAILED`; store not available and timeout → `UNREACHABLE` (or `AUTH_FAILED`)? Name the code for "locked" separately if it differs.
- [major] FR-006 / Edge case "Trust store password and end-to-end credentials" vs `ConfigValidator` – Some startup checks read variable values today, and with a lazy store read they have no input. (1) A trust store password on a node with CLI is a startup error today (`checkCredentials`). The spec says it "stays an error" but not when: at first use, in `--check-config`, or both? (2) An `http://` `e2e.soap.baseUrl` together with e2e credentials that are set is a startup error today (`e2eCredentialVariables`; Parameter Store uses the configured names). The credential store has no configured names, so this check is lost. (3) A trust store password without `tls.trustStore` gives a warning today. – Say for each check when and where it is made for credential store nodes. For example, (2) could become "`http://` with `e2eTests` ≠ FORBIDDEN on a credential store node is refused at the first `run_e2e_test` if end-to-end entries exist, and is reported by `--check-config`".
- [major] Edge case "Trust store password and end-to-end credentials" – "One of the two without the other is an error of that call" changes today's environment behaviour. Today `CredentialResolver.e2e` silently uses no basic authentication when one of the two is missing. – Confirm that this change is intended and list it in the migration notes, or keep the current behaviour.
- [major] FR-005 / US3 AS4 – The "source-neutral key name" is not named, so US3 AS4 cannot be tested. There will also be three places for the profile-wide prefix: `credentials.envPrefix`, the new key, and a top-level `source: { type: credentialStore, prefix }`. 010 had a rule only for `envPrefix` against a top-level `source.prefix`. – Name the key (e.g. `credentials.prefix`) and give the full precedence and conflict rule for all three. Also: does the default `INUBIT_<PROFILE>` and its pattern `^[A-Z][A-Z0-9_]{0,63}$` apply unchanged?
- [major] FR-008 / FR-006 / Edge case "The store asks the person" – It is unclear how much the person is prompted and how long they wait. The macOS Keychain asks per item. The first use of one node reads up to 3 kinds × 2 names, and a fan-out over N nodes can open many dialogs at the same time. After a "Deny", the 30 s back-off ends and the next call prompts again. Is the 60 s timeout per entry or per node read? – State: the timeout bounds the whole read of a node; dialogs are not opened in parallel (or at most one per entry at a time); after "access denied" no new dialog for 30 s (or until …). Also give the upper bound of a fan-out call while a dialog is open, given the default request `timeout` of 5 s and the fact that 010 counts the fetch time in each node's deadline.
- [major] Assumptions "Optional live checks against a real store may be added" vs US1/US2 Independent Test ("an opt-in check reads real entries") and SC-001/SC-007 – With test doubles only, nothing ever checks the identity mapping, the encoding or the dialog behaviour on a real store. SC-007 and SC-001 can then not be shown. – Make one opt-in live check per OS a required deliverable (as the US Independent Tests say), or reword SC-001/SC-007 to what the doubles can verify.
- [major] SC-001 / Clarification Q4 "keep working without migration" – The entries need no change. But unless the server reads them through `/usr/bin/security` (which the Assumptions leave to the plan), the trusted-application list of entries created with `security add-generic-password` does not cover the reading program, and macOS asks again at least once per entry. – Reword SC-001: "… after allowing the one-time Keychain access request for each entry". US1 AS1 should mention that dialog too.
- [minor] US2 AS3 vs Edge case "The store asks the person" – For a locked keyring, one text says it fails as "no usable credential store" and the other says the read waits for an unlock prompt. – Define it: a locked store that can show an unlock prompt waits (FR-008); one that cannot (no prompter, no session bus, SSH session on macOS) fails at once as "store not available".
- [minor] Assumptions "Default store per system" vs Edge case "Several entries" / Out of Scope – The Assumptions say "login keychain" and "default collection", but the system tools' default lookup searches the keychain search list or all collections. – Say which applies: only the default keychain/collection, or the system's default search.
- [minor] FR-003 / US3 AS2 – It is unclear which names are reported: only those of credential store nodes, or also those a Parameter Store node would have derived (a typical leftover after moving production to Parameter Store)? Are `TRUSTSTORE_PASSWORD` and the E2E kinds included? It is also not said that today's "`<PREFIX>_*_PASSWORD` matches no node (typo?)" warning is dropped. – State the name set, and drop or keep that warning explicitly.
- [minor] FR-005 – "The collision checks of today" leaves out the check for a node named `e2e` (`checkE2eNodeNames`: its `_E2E_USERNAME` group entry is also that node's username entry). It also leaves out the warning-only case of a file with the same `profile.name`. – Name both as kept for the entry names.
- [minor] US4 AS1 vs FR-011 – The outcome lists differ (`not checked` is missing in US4 AS1). FR-011 also leaves out the outcome of a timeout caused by an unanswered dialog, compared with "access denied" (exit 1 vs exit 0). – Align the lists, and state that a dialog left unanswered in `--check-config` counts as `not checked`.
- [minor] FR-009 / US5 – With a 60 s store timeout and a possible dialog, the re-read on the rejected call can add up to 60 s, not 10 s as for Parameter Store. – State the bound for the credential store.
- [minor] FR-015 – `docs/migration-001-to-002.md` (21 references to variables and `envPrefix`) and the hint in `Format001Detector` ("add credentials.envPrefix: INUBIT") are not covered. Neither is the `--help` text in `Launcher` ("--check-config … variable …"). The `get_health` text "still fetching from AWS Parameter Store" needs a credential store variant. – Add them to FR-015 and FR-010.
- [minor] FR-002 / SC-002 – Nothing is said about what happens to existing tests and fixtures that supply credentials through environment maps (`CredentialResolver`, `ConfigValidator`, `Launcher`, `LiveTarget` tests). – Add one sentence: they move to the store test double, and no test keeps a variable-based credential path except the SC-002 negative test and the FR-003 warning test.
- [minor] Plan risk (not for the spec) – Reading the stores from the JVM needs either native calls or subprocesses. Native calls to the Keychain make `java` the requesting program, so "Always Allow" may be lost with every JDK update or for an unsigned runtime. A `security` subprocess keeps today's permission but needs care with stdout and argv (FR-012). Secret Service needs D-Bus (`DBUS_SESSION_BUS_ADDRESS` from the client's environment, missing in GUI-less sessions). KWallet offers Secret Service only in recent versions. Windows needs `CredReadW` and has no built-in read tool. `cmdkey /pass` without a value prompts, so the docs can avoid the command line. Any new native-access dependency needs a license and a justification (Constitution, Technology & Security Constraints).
