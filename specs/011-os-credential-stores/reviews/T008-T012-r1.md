Stage 1: departures judged acceptable

- `SecretSourceConfig.SystemStore` instead of `CredentialStore` (data-model, plan, R-6, T008). A nested `CredentialStore` would share its simple name with the `config.CredentialStore` port in the same package, which is a real readability hazard. Acceptable, but the design documents should say so (nit below).
- `Source`/`ParameterSource`/`EntrySource` inside `NodeSecrets` instead of a top-level `SecretReader`/`ParameterReader`/`EntryReader`. Same split, same seam. Acceptable.
- The CLI and e2e rules run after the entries are read, so a dialog may open for an entry that is then refused. The entry has to be read to know it exists (R-11), so this is unavoidable.
- The intermediate build is inconsistent: the type is `credentialStore` and the validator texts say "store the value in the credential store", while `CredentialResolver` still reads environment variables until T014. Explicit `type: environment` configurations, including the fallback documented in docs/setup.md §4, now fail to load. This is acceptable because tasks.md forbids releasing anything before Phases 6, 7 and 9, and T021/T022 rewrite the docs. Plain users without an explicit type keep working, because the derived names are unchanged.
