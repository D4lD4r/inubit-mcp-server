FINDINGS:
- [major] Assumptions ("Module names are unique per owner") / FR-002, Edge Cases "Module names": the assumption contradicts the code base. `src/main/java/de/dadecker/inubit/mcp/application/ModuleUsage.java` javadoc: a module name shared by several modules of the owner is "not seen on the recorded node, but INUBIT does not forbid it"; `InventoryService` handles it (`sharedNames`, plugin-type match) and `moduleLookup` takes the first entry with the name. A `Module` entry carries only the name, so with a shared name the spec leaves open which module is "managed". Question: when several modules of the owner share a linked name, is the match narrowed by comparing the element's `ResourceType` with the module's type, and if still ambiguous, do all of them get "managed" with a warning that the link is ambiguous? Proposed wording: replace the assumption by "INUBIT allows several modules of an owner to share a name; a linked name matches a module only if the name is equal and the element's `ResourceType` matches the module's type; if more than one module still matches, each one's section says 'managed' and warns that the link cannot be attributed to a single module."
- [major] FR-002/FR-003/FR-004, Edge Cases "The check cannot be completed": the spec does not say which status applies when one element links the module but another system diagram or element could not be read. "Never 'not managed' when incomplete" is defined, but whether a partial hit is "managed" or "unknown", and how FR-007 (managed more than once) applies then, is not. Proposed wording: "If at least one read element links the module, the status is 'managed' with `complete: false`, the first system diagram or element that could not be read and the number not read; the warning about multiple management cannot be ruled out. 'unknown' only when no link was found and the check was incomplete."
- [major] FR-008 / User Story 2: `read_model_details` (action `module`) takes `target` (one server), `diagram` and `moduleId`; today it does not use `inventory.owner`, and nodes without an owner are valid for it (ConfigValidator only warns for inventory tools). The spec checks "the owner's system diagrams" but does not define (a) whose system diagrams are checked for `read_model_details`, (b) what happens on a node without `inventory.owner`, (c) what happens if `diagram` belongs to another owner than `inventory.owner`. Question: does `read_model_details` use the server's `inventory.owner`, and on a node without one return status "unknown" with reason NOT_CONFIGURED while the module's own properties stay as today? Is a diagram of another owner checked against `inventory.owner`'s system diagrams anyway, or "unknown"? Add as an acceptance scenario of US2 and an edge case.
- [major] FR-009 / User Story 3: marking "not found" names needs the owner's module list (StartCLI module index), which a diagram detail does not need today. The spec does not say what happens when the module list or an element's detail cannot be read in the system diagram detail. As written, an unread module list could mark every name "not found", the kind of unchecked claim the spec forbids elsewhere. Proposed wording: "If the owner's module list cannot be read, linked names are shown without a found/not-found mark and the list states why (error kind, what happened, what to do); if an element's detail cannot be read, the element appears with its name and the error instead of type, settings and modules; the diagram's other fields stay as today."
- [minor] FR-001 / SC-002: "100% of module results" does not say whether a NOT_FOUND item (with similar names) or a server `error` entry carries a management section. Proposed: "every successful module detail carries the section; NOT_FOUND items and server errors do not."
- [minor] FR-015 / User Story 2: `read_model_details` has no `refresh` parameter, and its module properties are read live while the management section may come from the cache. Question: does the section in both tools state its own `collectedAt`, and is the only way to bypass the cache for `read_model_details` a `get_inventory_item`/`list_inventory` call with `refresh`? If so, write it down. Also say whether the system diagram reads share the existing `find_partners`/`PartnerService` system diagram cache or the inventory cache, or leave it explicitly to the plan.
- [minor] User Story 1 AS5: "so the difference is visible field by field" can be read as the tool computing a cross-server diff. Proposed: "each server's result shows its own central settings; the tool does not compute a cross-server comparison." Context also says comparison across stages is "part of the use case" while `get_inventory_item` takes one stage; state whether cross-stage comparison is out of scope (one call per stage).
- [minor] SC-005: "within the tool's existing deadline" could forbid the plan to extend the module deadline (feature 018 extended the diagram deadline for its partner read). Question: may the plan add a budget for the system diagram read to the `get_inventory_item`/`read_model_details` deadlines? If yes, reword to "within the tool's deadline as extended by the plan for this read; reaching it gives 'unknown', not a TIMEOUT of the whole result."
- [minor] SC-001: "an agent ... in 10 out of 10 runs" does not name agent/model, prompt or who runs it, so it is not reproducible. Proposed: "In a manual acceptance run with the operator's agent and the prompt 'Where does module Demo-HTTP-Out-A send its data?' against the fake server of US1, 10 of 10 answers name `https://central.example.test`."
- [minor] FR-008 vs US2 AS2: FR-008 excludes "system diagram elements" in general, AS2 covers only `sdExtSystem`. Say how a system diagram element is recognized (e.g. `diagram` is of type `systemdiagram`, or the module type starts with `sd`) and that communication clouds and inubit systems are excluded too.
- [minor] Scope: no explicit Out of Scope section; boundaries are spread over Assumptions. Proposed section "Out of Scope": markers in `list_inventory`/`export_artifacts`; a new tool; changing central settings; deciding which value INUBIT applied at runtime; comparison across stages within one call.
- [minor] Terminology: "owner" is used throughout but not defined. Add: "owner = the server's configured `inventory.owner`, as in `get_inventory_item`."
