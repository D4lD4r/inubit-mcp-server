- [major] US2 AS1, Key Entities "Secret source", US2 narrative vs Clarification Q3 / FR-004 – Contradiction: AS1 and Key Entities speak of a "parameter path"; Q3/FR-004 say each group/node gets an explicit parameter name, no derived scheme. – Is there a path prefix joined to relative names, or are all names full and "path" dropped? If no prefix: AS1 "a region and explicit parameter names for every node"; Key Entities "(prefix; region, optional AWS profile)".
- [major] FR-006 / Edge case "node-level name wins" – Precedence for Parameter Store unclear (env vars fall back by value today). – If a node-level name is configured but the parameter is missing/empty, fall back to the group-level parameter or error? Proposed: precedence on configured names only; missing parameter is an error, no fallback.
- [major] FR-001 / FR-003 / US1 AS3 – Overrides undefined: (a) own env prefix per group/node? (b) own AWS region/profile per group/node (e.g. production in another account)? (c) what counts as a "contradiction" in US1 AS3? (d) one source per node for all kinds, or per kind? Proposed: "An override replaces the whole source of a group or node, including its settings; all secret kinds of a node come from the same effective source."
- [major] FR-006a / SC-006 / Q1 – "First use per node" unclear: (1) `get_health` without target and other fan-out tools address every node incl. production, so production secrets would be fetched whenever such a tool runs, against Q1's motivation; (2) what one fetch covers (all kinds at once? e2e credentials only for run_e2e_test? trust store password is needed to build the TLS context before the first REST call). – Does a fan-out count as use of every node? If not, what is reported for unloaded nodes? Do tools without credentials trigger a fetch? Proposed wording: fetched the first time a call needs to authenticate to that node (incl. each node of a fan-out); username, password, trust store password together; e2e credentials only when an e2e test runs.
- [major] Edge cases "trust store password and e2e credentials follow the same naming rules" / "no parameter name configured" – Meaningless for explicit names; optional kinds not stated as optional. – Proposed: for Parameter Store, trust store password and e2e credentials are read only if a name is configured, else absent; missing username/password names are a startup configuration error.
- [major] FR-010 / US4 AS1 vs US4 Independent Test – Contradiction about the retry (AS1: wait the 60 s pause; Independent Test: next call uses the new value while the protection holds; "at the latest" hints at proactive refresh). – (1) After a rejection with a changed re-read value, one login right away or only after the pause? (2) Does the rejected call fail or retry automatically? (3) Any time-based refresh? Proposed: re-read once; changed → pause lifted, next call (not the failed one) logs in with the new value; unchanged → 60 s pause; no time-based refresh. Also confirm US4 (P3, "acceptable for a first version" without it) is in scope since FR-010 is a MUST.
- [major] US3 Independent Test / FR-009 – "exits with the documented code" but none documented (today 0/1/2). – Proposed: exit 1 if a required parameter is missing, access denied or invalid; exit 0 with a warning if resolvability could not be checked because AWS access is unavailable. State whether the check reads and validates values or only checks existence.
- [major] FR-011, Edge cases "bounded back-off" / "bounded by a timeout", SC-005 "no more than a few seconds" – No measurable figures. – Store timeout and back-off after a failed fetch (e.g. 10 s timeout, no new attempt for 30 s per node), profile-configurable? Proposed SC-005: with a stub answering within 1 s, the first call takes at most 2 s longer than with env vars; later calls no measurable extra time.
- [major] US2 AS3 – "[default assumed: with a warning recommending encryption]" is an open assumption in an acceptance scenario. – Confirm; say where the warning appears; whether other types (`StringList`) are refused; remove the bracket.
