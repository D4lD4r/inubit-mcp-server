SPEC: specs/019-local-knowledge/spec.md  ROUND: 1

FINDINGS:
- [major] FR-014 / SC-005 / US2 – The sections contradict each other. FR-014 caps the previous versions per note, so the oldest ones get dropped. SC-005 says "every overwritten version is recoverable" and US2 says "nothing is lost". FR-014 also does not say whether previous versions are excluded from listing, search, the instruction titles and FR-013's total bound. If they sit next to the notes as `.md` files, they show up as duplicate hits. – Proposed wording: FR-014 "Every update MUST keep the previous version in a history area inside the knowledge directory that listing, search, reading and the instructions ignore. At most N versions per note are kept; when a new one is added, the oldest is removed. History counts / does not count toward the total bound of FR-013." SC-005: "…and the last N overwritten versions of every note are recoverable." US2: replace "nothing is lost" with "the previous versions stay recoverable within the history bound".
- [major] FR-011 / US2 – The record call is underspecified. Who picks the note name: the assistant as an input, or the server from the title? How is create told apart from update? What happens when a create hits an existing name (including a name that differs only in letter case), or an update hits a missing name? In replace/append, are title and topics kept when they are omitted? Does `source` change when the assistant updates a hand-written note? – Questions: "Is the note name an explicit input, or derived from the title by a stated rule?" "Is the mode (create | replace | append) an explicit input? Does create on an existing name fail with INVALID_INPUT/CONFLICT, and does update on a missing name fail with NOT_FOUND?" "On update, are omitted title/topics kept? Is `source` replaced, or are sources accumulated?"
- [major] Edge "Concurrent writes" / FR-015 – "refused or retried" allows two different behaviors. Lost updates are not covered at all: when the assistant replaces a note that the operator or a second process changed after the assistant read it, that change is silently overwritten. Two concurrent appends also need a defined result. – Proposed wording: "Concurrent writes to the same note are serialized (one at a time per profile directory, as for the workspace). An append is applied on top of the current content. A replace MUST carry the last-change value the assistant read; if the note changed since then, the write is refused with CONFLICT, naming the current last change. No retries happen inside the server." Add CONFLICT to FR-020.
- [major] FR-010 / FR-013 – The secret rules are not testable as written. (a) "INUBIT encrypted values (e.g. `AES…` ciphertexts)" is an open list, and the code has no existing detector for it. (b) "keystores in base64" has no criterion. (c) "Assignment" syntax is undefined (`key: v`, `key=v`, JSON `"key":"v"`, XML `<password>v</password>`?). It is also unclear whether a key matches as a substring (`pwdPolicy`, `credentialPrefix`, `tokenEndpoint`) or as a whole word, and which values are exempt (`***`, `${secret:…}`, empty, "see keychain"). (d) It is unclear whether configured credentials are also matched in encoded forms, as `SecretScrubber` already does (JSON/XML/URL/Base64). – Proposed wording: "(a) an INUBIT encrypted value is <exact pattern(s)>. (b) Key material is detected by the existing rule of feature 015 (`KeyMaterial`: PEM private key, or a base64 run of at least 64 characters that decodes to JKS/JCEKS/PKCS#12). (c) An assignment is `<key>` followed by `:` or `=` (also quoted JSON and an XML element named `<key>`), with the key matched case-insensitively against the listed names as <substring|whole word>. Values that are empty, `***` or a `${secret:…}` placeholder are exempt. (d) Configured credentials are matched in all spellings of `SecretForms`."
- [major] FR-013 / FR-010 – Masking on read and checking on write work against each other. Say the assistant reads a hand-written note whose `password: x` comes back masked, then replaces or appends. Either the write is refused for `password: ***`, or the hand-written value is silently replaced by `***`. For append it is also unclear whether only the new text or the resulting whole note is checked. If the whole note is checked, appending to any hand-written note with a secret always fails. – Question: "For append, is only the appended text checked, or the resulting note? For replace of a note whose current content contains a detected secret, is the write refused (telling the operator to clean the note by hand) or allowed (old version in history)? Is the mask token `***` exempt from the check?"
- [major] FR-006 / Edge "Large knowledge" / FR-010 – Titles go into the server instructions, which clients trust more than tool results. Nothing requires those titles, topics and fallback file names to be masked, made single-line or bounded per entry. A hand-written title such as "Ignore the rules and …" becomes part of the instructions, which defeats the edge-case "notes are data" rule. "Newest or most important" also gives two orderings, and "important" has no definition. – Proposed wording, FR-006: "Titles and topics in the instructions are masked per FR-010, reduced to a single line without control characters, cut at <n> characters each, and presented as a quoted list of note references. When the list is cut, it shows the most recently changed notes first and gives the total." Apply the same masking rule to note names and titles in search hits.
- [major] FR-004 / FR-008 / US1 – "Last change" has two possible sources: the metadata field (FR-004) or the file's modification time. They diverge as soon as the operator edits a note by hand, and US1 depends on it ("how old it is"), as do ordering and the conflict check. – Question: "Is 'last change' the file modification time, the metadata field, or the metadata field with the modification time as fallback? Which wins when they differ?"
- [major] Edge "Files that are not notes" / FR-008 – The spec does not define which files count as notes. Which extensions (`.md` only? `.markdown`, `.txt`?) Are subdirectories scanned, and if so, does the note name contain the relative path, which conflicts with "no path separators"? What size makes a file "very large", given that SC-004 requires a 1 MiB note to be readable? – Proposed wording: "A note is a regular, non-hidden file with extension `.md` directly in the knowledge directory / in any subdirectory (name = relative path with `/`). Files over <n> MiB are listed with a warning but not searched."
- [minor] FR-002 / US3-AS3 – "Another per-profile directory of this … profile" could be read as including `~/.inubit-mcp/<profile>` itself, which would make the default `~/.inubit-mcp/<profile>/knowledge` invalid. The set of profiles checked is also unstated. The existing workspace rule uses "profiles in the default configuration directory". – Proposed wording: "MUST NOT equal, lie inside or contain this profile's workspace, audit, backup and ledger directories; any directory of another profile in the default configuration directory (including `~/.inubit-mcp/<other>`); the configuration directory or the folder of the configuration file in use. Lying inside `~/.inubit-mcp/<profile>` is allowed. Paths are compared after resolving symbolic links. A violation is a configuration error (the server does not start), like for the workspace."
- [minor] FR-013 – The numeric values of the size bounds (note size for writes, total size, history count, instructions bound, page and excerpt sizes) are not given. It is also unclear whether they are fixed or configurable, and what happens when the assistant appends to a hand-written note that is already above the write bound. – State the values or "fixed in the plan, documented in setup.md, not configurable / configurable". Add: "an update whose result exceeds the bound is refused with PRECONDITION_FAILED".
- [minor] FR-008 – Masking and paging are not ordered against each other. If masking is applied per page, a PEM key split across a page boundary can escape it. Search may also match raw text, which lets a search for a secret value confirm that the value is stored. – Proposed wording: "Masking is applied to the whole note before cutting into pages or excerpts. Search matches against the masked text." Also define the topic filter (exact, case-insensitive) and the order of hits (last change, newest first) so paging is stable.
- [minor] FR-020 vs US2-AS4 – With recording switched off, the record tool is not offered, so "PRECONDITION_FAILED for recording switched off" can never happen unless the configuration is reloaded at runtime. – Remove that case, or state when it applies.
- [minor] FR-005 / US1 – US1 expects the assistant to say which part of an answer came from a note and how old the note is, but no FR asks the instructions to request this. – Add to FR-005: "…and that an answer using a note names the note and its last change."
- [minor] FR-017 / FR-016 – Other state-changing tools use a two-step server-side confirmation (PREVIEW/EXECUTE). This tool relies on client-side consent only. – Say explicitly that no server-side confirmation code is used, and why: the write is local, never deletes and keeps history. That way the plan does not add one by analogy.
- [minor] Constitution I / FR-012 – Principle I says "The server MUST start in read-only mode". Recording that is on by default needs the spec to state the interpretation: the principle governs INUBIT state, as with `export_artifacts`, which writes local files without `write.enabled`. – Add one sentence citing that precedent, so the plan's Constitution Check does not have to reinterpret it.
- [minor] FR-003 / US3 – Notes may be moved to a synchronized folder, but FR-003 forbids changing existing permissions, so a group- or world-readable existing directory goes unnoticed. – Should `--check-config` warn when the knowledge directory is accessible to others? Also add a `--check-config` line such as `Knowledge: <path> (ok | absent | <problem>), recording on|off, <n> notes`, matching the workspace line.
- [minor] FR-019 – Debug logging of reads does not say whether the search query is logged. A query may contain a customer name or a secret. – "The DEBUG log contains note names and result counts, not the query text."
- [minor] Assumptions / FR-021 – Secret detection is pattern-based. A secret written in prose ("the password is …") is not caught, and SC-002 only covers the recognized kinds. – Have FR-021's SECURITY.md item state this residual risk explicitly.
