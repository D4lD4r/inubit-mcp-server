FINDINGS:
- [major] FR-013 / FR-019 / FR-020 / SC-002 – The note `name` is not checked for secrets on write. FR-013 checks only title, topics and content. The name rule (letters, digits, `_ . -`, spaces) still allows a configured credential typed as plain text, and it allows the FR-010(c) form `AES-` followed by 16 or more letters and digits. Such a name would end up unmasked in three places: the file system, the audit record (FR-019 records the "note name") and the DEBUG log (FR-019 "with note names"). Names of hand-written notes are also written into audit and log records, and into `NOT_FOUND`/`CONFLICT` messages, without masking. This conflicts with Principle II ("Secrets MUST NOT appear in ... logs") and with SC-002 ("zero such values end up in a note through recording"). – Proposed wording: in FR-013, "the secret rules apply to the `name` in every mode as well; a finding is refused with `INVALID_INPUT` (kind, 'name', never the value)." In FR-019 and FR-020, "note names in audit records, logs and error results (including the similar names of `NOT_FOUND`) are masked per FR-010, as in FR-006." Add a scenario to US2-AS4: "a `create` whose name contains a configured credential is refused".
- [minor] FR-015 / US2-AS9 – Neither says how long a second writer waits for the lock. AS9 requires both writes to succeed, so the second writer must wait, but "no retries" leaves open how long. A process that hangs while holding the lock, or a lock on a synced folder, would make the write wait forever. – Question: how long does a writer wait for the lock, and which error does it get after that? Proposed: "A writer waits up to 10 s for the lock; after that the write is refused with `PRECONDITION_FAILED` ('another write is in progress'); nothing is written."
- [minor] FR-004b / FR-011 `create` / Edge Cases – Some paths are occupied by something that is not a note. Examples: a hand-written `Partner.MD`, which is the same file as `Partner.md` on a case-insensitive file system; a directory `Partner.md`; or a symbolic link on an intermediate segment of `a/b`. The collision check only covers notes, so these slip past it. "A `create` never overwrites an existing file" says what must not happen, but the result is unspecified. – Proposed: "If the target path or one of its parent segments is occupied by anything that is not a note of that name (a file with another extension case, a directory, a symbolic link), `create` is refused with `PRECONDITION_FAILED` naming the occupying path; nothing is written."
- [minor] FR-011 `create` – The wording "also when only the letter case differs" is narrower than FR-004b, which also covers Unicode normalization. – Reword to "if a note of that name exists, compared as in FR-004b (NFC normalization and case folding)".

Round 2 replaced that with the version token, so the two decision lists contradict each other. – Reword the round-1 entry to "`replace` carries the version token read (see round 2)", or mark the entry as superseded.
