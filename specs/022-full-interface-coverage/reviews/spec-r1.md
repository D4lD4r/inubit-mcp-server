SPEC: specs/022-full-interface-coverage/spec.md  ROUND: 1

No [NEEDS CLARIFICATION] markers are left. The Out of Scope section is present and clear. I checked the spec against the constitution, against docs/tools.md (the existing write model, tag_artifacts, set_active, get_health, the export_archives folder rules) and against the backups section of docs/setup.md.

FINDINGS:
- [major] Background table vs. User Stories / FR-001, FR-002, FR-004 – Several table entries belong to no user story, so FR-001 cannot mark them "planned" with a story number. FR-002 still requires them to be reachable, and no acceptance scenario covers them:
  - `msglist`, `msgread`, `msgsend`, `msgdel`
  - `-ne`, `-nx`, `-nw`, `-nq`
  - `date`, `lls`, `-sv`, `-pctmem`, `-maintenanceState`
  - `process validateExport`, and `process resume` (named in US5, but no scenario covers it)
  - `export --exportWorkflowGroupExclude` and "reading a repository resource" (which endpoint?)
  - `import --importMetadata`, `POST /isconnector`, `PUT /keys`
  - `debug on|off` (is it part of "trace level" in US4?)
  - `tag --tagRemove|--tagDiagram|--tagRepositoryPath|--tagWorkflowGroupExclude`
  - setting the share of threads for privileged workflows
  - the start options `--backupFile` and `--backupRepository` (Assumptions)

  Proposal: add a column "User Story" to the Background table so every entry maps to exactly one story. For each entry, either add an acceptance scenario to that story or move the entry to the exclusion list now, with its reason.
- [major] FR-005 vs. FR-006 / SC-007 – FR-005 groups tools by task. FR-006 caps tools per area A–E, and the areas are object types, not tasks. US4 ("operate a server") spans areas A (maintenance, trace), D (`processdelete error`) and E (`--tagSetActive`). Under FR-006 one task would be split across three area write tools. Under FR-005 it would need one tool across areas. Question: is the limit per area, or a total (for example "at most 10 new tools, each justified by one user story")? Proposed wording for FR-006: "The feature MUST add at most 10 tools in total; each new tool serves exactly one user story, and the plan names it."
- [major] FR-005 ("tagging for the tag operations") and US4, US6 vs. the existing `tag_artifacts` and `set_active` – Both existing tools are development-stage tools (`NOT_DEVELOPMENT` elsewhere, never production). `tag_artifacts` deliberately never removes a tag, because StartCLI removes tags only for the whole owner, which could take away a tag that marks another group's state. US4 wants to set and remove the active tag version on operational servers (production with the opt-in) with write enablement only. US6 wants to delete tags. Questions: which protection applies when an existing development tool is extended, the development-stage gate or write enablement plus opt-in? How do `--tagRemoveActive`, `--tagDelete` and `--tagRemove` avoid the owner-wide removal that docs/tools.md warns about? Are they limited to an explicit scope, or excluded with that reason?
- [major] FR-002 vs. Constitution Principle V (REST preferred, CLI only where REST does not offer it) – The table lists the same function in both channels: `license -td` / `GET /license`, `delete --deleteWorkflow` / `DELETE /diagrams/…`, `delete --deleteUser` / `DELETE /user/users/{name}`, `library --delete` / `DELETE /libraries/{name}`, `user` / `GET /user/users`, and others. Read literally, FR-002 makes both reachable. In addition, `get_health` already returns `licensedThreads`, `maxBlockingQueueSize` and `maintenanceMode` over REST. Proposed addition to FR-002: "Where REST and StartCLI offer the same function for a version, the capability uses REST, and the StartCLI entry gets the state 'covered by <tool>'. Facts that `get_health` already returns are not fetched again."
- [major] FR-017 / US4 AS4 (`processdelete error`) – "The confirmation is valid only while that set is unchanged" cannot be guaranteed. `processdelete error` deletes whatever is in error when it runs, and on a busy server the set changes between preview, re-check and execution, so the confirmation may almost never succeed. Question: is a changed set refused (and then how is the window between re-check and execution handled), or is it tolerated with the result reporting the count actually deleted next to the previewed count? Proposed wording: "The execution re-reads the set right before sending. If it differs from the preview, the call is refused with a new preview. The result names the number INUBIT reports as deleted, which may include processes that entered the error state after the re-read."
- [major] US5 / FR-014 / FR-016 – It is not stated whether `process export` on the source counts as state-changing. The source of a migration is often production, and the archive holds business payloads. Questions: does the export need write enablement, the production opt-in and the run-time-data opt-in on the source, or only the folder rules of `export_archives` (including `archives.productionOptIn`)? Also, US5 AS2 names only "write enablement" for the import, while FR-016 also requires the run-time-data opt-in. Align AS2 with FR-016.
- [major] US3 AS5 vs. US5 – US3 AS5 lists blocked processes "of an earlier run-time data export". US5 says the import returns the operation id and creates the blocked processes on the target. This decides which server and which operation id the read takes. Proposed wording: "Given the operation id of an earlier run-time data import on that server, When the blocked processes are listed, …"
- [major] FR-020 vs. `ps -f '<filter>'` (US3 AS1) and the "filter expression" of `process export` (US5 AS1) – Both send a filter expression to a command line. A filter is neither a name nor an enumeration, so the rules of FR-020 do not cover it. Question: does the tool take structured fields (workflow, tag, state) and build the expression itself, or does it accept a raw expression checked against a fixed grammar? Proposed wording: "Filters are given as structured fields; the server builds the StartCLI filter expression from validated values only."
- [major] FR-021 and the upload edge case – "within the allowed folders" and "with a size limit" are undefined. No configured list of allowed source folders exists today; the `export_archives` folder rules cover output folders only. Questions: which folders may upload files come from (a new per-profile setting, the workspace, the same rules as `targetFolder`)? What is the size limit per file type, or its default if it is configurable?
- [major] FR-019 / Edge Cases ("the certificate in the keystore") – For bulk imports and key uploads the server cannot decide what "would remove its own access" means. `import --syncLDAPUsers`, `--overwriteUserRoles` and `--importUserGroup` may change the login user without naming it. `PUT /keys` may replace the TLS certificate that the server pins (feature 006). Questions: are bulk user, role and LDAP imports refused when the login user could be affected, refused always, or allowed with a warning? Does "key material its connection uses" mean any `PUT /keys` that touches the alias of the pinned certificate? Is a planned certificate rotation through this tool allowed, and how does it interact with the pin rotation of feature 006?
- [minor] Edge Cases (concurrency) – "the second is refused or waits" allows two behaviours, and "of the same kind" is vague. Proposed wording: "A second state-changing call against the same server and the same object (or the same bulk set) while one runs is refused with PRECONDITION_FAILED, as for restart_process."
- [minor] FR-015 – The existing confirmation also has a `CLIENT` mode (no server preview, not allowed on production). Question: does `CLIENT` apply to the new tools, or do the administrative areas always require the server preview (as `development.repository: WRITE` does)?
- [minor] FR-018 – Questions:
  - Can these new backups be restored with `restore_backup` on non-development nodes, or only by hand in the Workbench?
  - Does the 30-day retention apply to them?
  - What does "an export of a tag state" contain?

  Also state that objects INUBIT cannot export (libraries, license, configuration values) get no backup, and that their preview shows the current value instead.
- [minor] FR-001 / SC-001 – The granularity of an entry ("command and option group") and the source list of "documented" pages are not fixed, so SC-001 cannot be checked. Proposal: name the documentation pages for 8.1 and 9.0, and define an entry as one command plus one option, or one HTTP method plus one path.
- [minor] FR-002 vs. FR-025 – An entry can be reachable for 8.1 while 9.0 is not recorded yet. Question: does the coverage list carry a state per version (reachable on 8.1, planned on 9.0)?
- [minor] Edge case `POST /isconnector` vs. FR-002 – The exclusion reason "the payload cannot be built reliably" is not a result of "a check against a real system", which FR-002 requires. Either allow reasons derived from the documentation in FR-002, or state that the check must be done on a test system.
- [minor] US4 – The difference between maintenance mode (`maintenance on|off`) and readiness (`POST /ready/{on|off}`) is not explained, and the meaning of `-eq` is not given. Say what each means to the operator and whether `-eq` is offered.
- [minor] US6 – No scenario covers the license upload. Proposed: "the preview shows the current and the new expiry date and licensed threads; a license for another host or an expired license is refused before sending" (or whatever INUBIT can tell).
- [minor] US7 AS5 – "and what happens to them" leaves the expected content open. State the INUBIT behaviour (for example, ownership moves to the group, or deletion is refused), or say that the preview quotes INUBIT's documented behaviour.
- [minor] FR-011 / US2 AS2 – "state" of a user is undefined (active, locked, LDAP?). No scenario covers the personal fields that FR-011 allows for a single named user. Add one scenario.
- [minor] FR-010 – "every field whose name marks it as a secret" should refer to the existing secret-name rule of features 018 and 020, so there is one rule and not a second one.
