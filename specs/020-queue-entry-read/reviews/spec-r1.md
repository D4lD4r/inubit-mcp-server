FINDINGS:
- [major] FR-006 / SC-001 / Assumptions (9.0) – Conflicts with Constitution V. A version other than the 8.1 baseline may be declared supported for a capability only when that capability has contract tests against recorded responses of that version. For 9.0 the spike reached only the error-store lookup. No real 9.0 response containing a data stream and variables exists, yet FR-006 and SC-001 declare 9.0 supported. – Decide which applies: (a) "9.0 support is enabled only once a real 9.0 response for an ERROR entry (data stream plus variables) is recorded as a contract fixture; until then a 9.0 server is refused with `UNSUPPORTED_VERSION` ('not yet verified')", or (b) make that recording a release gate in the spec ("the feature is not released with 9.0 support before …"). Whichever you choose, record it as an FR, not only as an assumption.
- [major] FR-009 / Edge case "Text in an unknown or wrong charset" – The spec never says how text is told apart from binary. ISO-8859-1 decodes any byte sequence, so the charset fallback makes every stream "text", and scenario US1-3 (ZIP/PDF → binary hint) cannot be implemented deterministically. – Proposed wording: "Content is binary if it starts with a known signature (ZIP, GZIP, PDF, …) or if the first N bytes contain a NUL byte or more than X % control characters other than TAB/CR/LF. Otherwise it is text, decoded as UTF-8 if valid, otherwise as ISO-8859-1." Also: if INUBIT returns an encoding or content type for the entry, does it take precedence?
- [major] FR-011 / Background input "Secrets masked like exports" – The spec does not say whether secrets inside the business payload are masked (WS-Security `<Password>`, XML element or JSON key `password`, variable values that are documents). Constitution II says secrets MUST NOT appear in tool results. – Question: Is name-based masking also applied to XML elements, attributes and JSON keys in the data stream and in variable values (with which placeholder)? If not, state explicitly that third-party credentials in business data may appear, and add that to the opt-in documentation of FR-004.
- [major] US1-4 / FR-011 / SC-003 (audit log) – The spec never says whether a call writes an audit record; reads are not audited in the project. – Decide; if no, remove "audit log" from US1-4, FR-011 and SC-003. In either case add: "The data stream and variable values are never logged at any level; only sizes and the outcome are."
- [major] Edge case "Several entries for one process ID" / FR-005 – Ambiguous when one process ID has several entries of which only one is in ERROR. – Proposed wording: "Candidates are the entries of the process ID in state ERROR. If exactly one exists, it is read. With several, `INVALID_INPUT` listing them. With none but other entries present, `INVALID_INPUT` ('only ERROR entries are supported'), listing their states."
- [major] FR-003 (opt-in placement) – Not defined what happens on a node, in `defaults`, or with other keys under `unsupported`; inheritance from `defaults` would silently enable production groups. – Proposed: accepted only on a group; elsewhere or other key under `unsupported` is a startup error (unknown key) that does not echo the value.
- [minor] FR-001 vs FR-009 – per-call text limit not in FR-001; "configurable" ambiguous. – Add optional `maxChars` (1–100,000, default 20,000); say "no profile setting".
- [minor] FR-001 input validation – constraints for `fileName` and reuse of the `processId` pattern missing; group id rejected by schema.
- [minor] FR-016 – "configured client timeout" ambiguous. – Bounded by `cliTimeout`; waiting for a slot counts as for StartCLI.
- [minor] FR-010 – output shape for system variables open; rule for system variables and binary variable values undefined.
- [minor] FR-011 – placeholder for Authorization/Basic/Bearer values not named.
- [minor] FR-009/FR-010 – worst case ~500,000 chars; decide on an overall cap.
- [minor] FR-002 – existing announcement rules (pinned unsupported version, StartCLI installation) not addressed.
