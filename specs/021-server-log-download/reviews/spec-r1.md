SPEC: specs/021-server-log-download/spec.md  ROUND: 1
FINDINGS:
- [major] FR-010 / FR-009 / US1 scenario 3 – Masking scope versus line selection is not defined. The FR-011 rules from feature 020 work on whole texts: an element is masked from its start tag to its end tag, and a start tag with no end tag is masked up to the next `<`. If masking runs only on the selected tail lines or matching lines, it can miss a secret. For example, take `<password>` on line N and the secret on line N+1, where only line N+1 is in the tail or matches `contains`: the secret is returned unmasked, which breaks Constitution II. – Proposed wording for FR-010: "Masking is applied to the whole scanned window (FR-009) before lines are selected for the excerpt and before it is cut at `maxChars`; an element whose start tag lies before the window is not detected (documented limit)." Or state another rule that closes this gap.
- [major] FR-001 `contains` / FR-009 – The spec does not say whether `contains` is matched against the raw text or the masked text. If it is matched against raw text, a caller can find out credential values by searching for guessed fragments and reading the match count or line numbers, even though the shown lines are masked (Constitution II). – Proposed wording: "`contains` is matched against the masked text; a search text that only occurs inside a masked value yields no match."
- [major] FR-009 – Line numbers and the total match count are ambiguous when only the last 50 MiB are scanned. "Line number in the file" requires counting lines across the whole file, while "total number of matches" can only cover the scanned window. – Question: are line numbers absolute in the file (newlines before the window are counted without matching) or relative to the scanned window? Is the total "matches in the scanned window"? Proposed wording: "line numbers are absolute in the downloaded file; the match total counts the scanned window only, and the result says so when the window is smaller than the file."
- [major] FR-009 / FR-001 `maxChars` – The direction of the cut is not defined. The excerpt is a tail (latest lines last), so keeping the first `maxChars` characters would drop the most recent lines, which are the point of the tail. – Proposed wording: "When the selected lines exceed `maxChars`, whole lines are dropped from the beginning (oldest first) until the rest fits; a line longer than `maxChars` on its own is cut at its end; the truncation marker names how many lines were dropped."
- [minor] Clarifications / FR-002 / US1 scenario 5 – trace.log needs no opt-in (a decision by the creator, not yet confirmed by the owner), yet the Background says it contains "module output at debug level", i.e. possibly business data in clear text. It is also available on `production: true` groups with no warning. – Question for the owner: is trace.log without opt-in acceptable on production groups, or should the configuration summary at least list it there, as FR-016 does for the web service log?
- [minor] FR-014 / FR-002 – The spec does not say explicitly that the tool is not gated by the write-access flag or the production write opt-in (Constitution I covers only changes on INUBIT). – Add to FR-002: "The tool changes nothing on INUBIT and is therefore not subject to the write-access settings; it is offered in read-only mode."
- [minor] FR-015 – Constitution VII requires timestamp, target environment and sanitized parameters in audit records. FR-015 lists only tool, server, log, file path, size and outcome. – Proposed wording: "…(timestamp, tool, server, log, sanitized parameters incl. `tailLines`, `maxChars` and whether `contains` was given, file path, size, outcome)". Also decide whether the `contains` text itself is audited.
- [minor] FR-007 / FR-011 – When the target folder is created by the call and the call then fails, the spec does not say what happens to the folder ("no file remains"). The spec also does not say whether a name collision between two concurrent calls in the same second is resolved atomically. – Proposed wording: "a folder created by a failed call may remain (empty)" or "is removed"; "the free name is claimed atomically (create-new), so concurrent calls never share a name."
- [minor] US3 scenario 3 – "fails with the detection error" does not name a code. – Name the expected codes (e.g. `UNREACHABLE`, `TLS_ERROR`, `AUTH_FAILED`, as reported by version detection) so a test can check them.
- [minor] Edge cases "Empty log" vs US2 scenario 4 – The spec does not say how "file does not exist" (`NOT_FOUND`) is told apart from "file is empty" (empty file written) when the internal download does not tell the two apart. – Add: "If the interface does not distinguish a missing file from an empty one, the tool reports `NOT_FOUND` / an empty log (choose one)." Leave the exact detection to the plan.
- [minor] SC-001 vs FR-017 – SC-001 promises 9.0 for both logs without condition, while FR-017 allows 9.0 to be refused when no recording can be made. – Add "(subject to FR-017)" to SC-001.
- [minor] Edge case "Binary or non-UTF-8 content" – Feature 020 (FR-009) has a binary classification that never returns binary content. Here binary bytes would be decoded as ISO-8859-1 into the excerpt. – Question: should a window that would be classified as binary under feature 020's rules return only size and a hint, for consistency?
