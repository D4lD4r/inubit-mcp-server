FINDINGS:
- [major] FR-001 / FR-016 vs. Assumptions (first bullet) and Constitution Principle V – The read channel is fixed to StartCLI in two places. FR-001 only offers the tool on nodes with a StartCLI installation, and FR-016 says "channel StartCLI". But the Assumptions leave open whether REST `/model/export` also carries `PartnerManagementSettings`, and Principle V makes REST the preferred channel. docs/tools.md (around line 989) shows `get_inventory_item` already reads diagram details through REST `/model/export`, so REST is a real candidate. As written, the plan has to break either the spec or the constitution. – Either give the evidence that REST cannot deliver the Partner Management (then StartCLI is justified), or reword FR-001 and FR-016: "The channel is REST if the plan's research shows that `/model/export` of a system diagram contains `PartnerManagementSettings`; otherwise StartCLI. The tool's availability condition (FR-001) and the capability's channel (FR-016) follow that decision."
- [major] FR-006 / FR-012 / FR-017 / US3 – The spec does not say how comparison combines with list mode and paging. Open questions: (a) A comparison without a search term: does it show the summary (FR-006) or full details? If it shows the summary, SC-003 ("shows every differing setting") cannot hold. (b) What do `total` and `nextOffset` count in a comparison: the union of matched partner keys across all servers, or the partners of each server? (c) The search compares against which server's values? Example: `Name` matches on stage A but differs on stage B; does the matched partner from B appear too? (d) What happens if the compare target equals or overlaps `target`: `INVALID_INPUT`, or deduplicate? – Answer (a) to (d) and add the answers to FR-012 and FR-017. Proposed: "Paging and `total` count matched partner keys (FR-013) across all compared servers; a partner is included if the search matches its non-secret fields on at least one server; a comparison always compares all settings, and without a search term it shows only the settings that differ plus the summary fields."
- [major] FR-002 / FR-005, US2 scenarios 2 and 3 – The filters have no defined matching rules. The research describes `protocol="FTP"` combined with `FTPProtocol=SFTP`. Does `protocol: SFTP` find anything? Is matching exact or substring, and case-sensitive or not? Does the system-diagram filter use the name only or also the diagram group? Is the workflow filter an exact workflow name? Only an unknown system diagram is assigned an error (`NOT_FOUND`, FR-019). Is an unknown protocol or workflow an empty result or an error? – Proposed: "Filters match case-insensitively and exactly: `protocol` against the `ReferencedTWF` attribute `protocol` only (not `FTPProtocol`), `systemDiagram` against the diagram name, `workflow` against the referenced workflow name. An unknown system diagram gives `NOT_FOUND` with `similarNames`. A protocol or workflow without matches gives an empty result."
- [major] FR-012a, US3 scenarios 4 and 5, SC-003 – The equality statement for secrets assumes that equal passwords have equal stored forms on different servers and stages. If INUBIT uses a per-installation AES key or a random IV/salt, every set password is reported as "differs". Scenario 5 could then never occur on real data, and the result would mislead the operator. – Question: Is INUBIT's stored form of a `Password` property deterministic across servers and stages (same key, no random IV)? Add it as an Assumption or a plan research item, and add a fallback: "If the plan's research shows that stored forms of equal secrets are not comparable across the compared servers, the comparison makes no equality statement for secrets and says why."
- [major] US1 scenario 6 (no FR) – The "up to five similar partner Ids or names" suggestions appear only in a scenario. No FR defines how similarity is computed, and no FR restricts suggestions to non-masked fields. FR-011 only protects the search. Suggestions drawn from a masked custom partner field would leak secret values (Principle II). – Add an FR: "If a search matches no partner, the result lists up to five `similarNames` taken only from non-masked `Id` and `Name` values of the read system diagrams, using the same rule as `get_inventory_item`'s `NOT_FOUND` (contains, contained-in for at least 3 chars, edit distance max(2, length/3), closest first)."
- [minor] FR-012b vs FR-010 – FR-012b allows a comparison without a fingerprint that "reads the values it compares in one call". That needs raw secret values outside the parsing component, which FR-010 forbids. – Either delete the alternative, so the keyed fingerprint is always used, or add: "in that case the parsing component itself computes the server groups and passes on only the groups."
- [minor] FR-003 vs Edge Cases ("Export trace") and Assumptions – FR-003 says no state on INUBIT may change, but the export changes the check-in comment suffix. – Reword: "…or any other state on INUBIT, except the export trace in the check-in comment accepted in Assumptions."
- [minor] US1 narrative ("authentication kind") – The term is undefined, and Out of Scope excludes interpreting authentication. – Reword: "the authentication-related settings as configured (e.g. `Auth`, `FTPAuth`, `FTPProtocol`), shown as values without interpretation."
- [minor] FR-006 / US2 scenario 4 ("server and login per entry") – For WebService and unknown protocols it is unclear which settings count as "server" and "login". – Proposed: "the protocol settings `ServerName` and `Login` if present, otherwise omitted." Alternatively, name the per-protocol keys.
- [minor] FR-004 vs FR-009 – A partner field masked by name: is it omitted (FR-004 says "every non-secret partner field") or listed as masked with "set"/"not set" (FR-009)? – State which.
- [minor] FR-008 name pattern `keystore` – `SSLKeyStore` is probably a keystore reference, and masking it hides part of the "which authentication" answer the support case needed. – Confirm that this is accepted, or let values of `SSLKeyStore` that are not key material be shown.
- [minor] FR-002 validation – Validating the search term "as for the existing diagram names" may reject real partner names (umlauts, `&`, `/`). – Give the search term its own rule (length limit, printable characters, no control characters).
- [minor] FR-002 owner default with stage or compare targets – `inventory.owner` can differ per group or node. – State that the owner is resolved per server (or that an explicit `owner` applies to all compared servers), and that a server without an owner fails alone with `NOT_CONFIGURED`.
- [minor] FR-013 – Matching uses the system diagram name only. Two system diagrams with the same name in different diagram groups would collide. – Add "and diagram group", or report this as ambiguous.
- [minor] FR-020 – For a stage or comparison call: one audit record per call or one per server? FR-021 is per server. – State which, and how the counts are split.
- [minor] FR-018 – In a comparison, is the collection time given per server? – Proposed: "`collectedAt` per server."
- [minor] Missing acceptance scenarios – FR-007 (`ReferencableTWFs`, diagrams without a Partner Management), FR-016 (6.1 refused, 9.x warning), FR-018 (`refresh`, shared concurrent export), FR-020 (audit write failure leads to `INTERNAL` without data) and FR-019 have no Given/When/Then. – Add at least one scenario each, for example under US1 or a new "Operational" block.
