FINDINGS:
- [major] FR-006 (also used by FR-012c and story 2 scenario 4) – The required fields of the list summary were not updated for communication clouds: they are "system diagram, partner fields, and per entry protocol, workflow, `ServerName`, `Login`". The edge case "Several communication clouds" says the same `Id` in two clouds is two partners. Without the cloud, two summary rows look identical, and so do two unmatched partners in a comparison without a search term. – Proposed wording: "A list without a search term MUST show a summary per partner: system diagram (name and diagram group), communication cloud (module name), partner fields, and per entry …". Research found `ServerName` and `Login` for both FTP and WebService, so the parenthesis about protocols that name these differently can become: "the summary keys are `ServerName` and `Login` for every protocol (research D-2)".
- [major] FR-008 / Edge case "A partner field holding a secret" – The recording shows that `PartnerFields` declares each configured field with a `fieldType` attribute (research D-2 facts). FR-008 masks a partner field only by its own property attributes (`type`, `encrypted`), its name or its value. It ignores a password-like type declared in `PartnerFields`. If INUBIT allows a field typed as a password, its value could be shown in clear when the value property carries no `type="Password"` and the name is harmless (Principle II, non-negotiable). – Question: which `fieldType` values can INUBIT assign to a partner field, and can any of them hold a secret? Proposed wording to add to FR-008: "its partner field is declared in `PartnerFields` with a `fieldType` that is not one of the plain types listed in the research (allowlist; any other or unknown `fieldType` is masked)".
- [minor] FR-004 / FR-012 – The recording found a further entry attribute, `format`, of unknown meaning. Research says the tool shows it as an entry attribute, but FR-004 lists only protocol, workflow, protocol settings and additional parameters, so the spec does not say whether it is shown or compared. – Add to FR-004: "and its other attributes (e.g. `format`), uninterpreted"; and to FR-012: "entry attributes other than `protocol` and the workflow reference are compared like settings". Or state explicitly that they are left out.
- [minor] FR-013 / Edge case "A `ReferencedTWF` whose workflow reference does not resolve" – An unresolved entry has no workflow name, so its comparison key and how the `workflow` filter treats it are undefined. – Proposed wording: "An unresolved entry never matches a `workflow` filter; in a comparison its key is (protocol, unresolved), it is matched by position among unresolved entries of the same protocol, and the match is reported as uncertain." Alternative: "it is never matched and is reported as 'only on <server>'".
- [minor] Key Entities "Communication cloud" / FR-013 – A cloud is identified by its module name, but the spec does not say whether module names are unique within one system diagram. Research saw a `ModuleId` as well. – Question: can two `sdCommunicationCloud` modules in one diagram have the same `ModuleName`? If yes: "clouds with the same module name in one system diagram are told apart by `ModuleId` in the result; a comparison reports them as ambiguous (FR-013) instead of matching them".
- [minor] Acceptance scenarios (stories 1 and 3) – The cloud level in FR-004 and FR-013 is covered only by an edge case, with no Given/When/Then. – Add, e.g. to story 3: "**Given** a system diagram with two communication clouds that both hold partner `ACME-0001`, **When** searched on a stage, **Then** two partners are returned, each naming its cloud, and each is compared only with the same cloud on the other servers."
- [minor] FR-001, FR-003, FR-010, FR-016, FR-019, Edge case "Slow or failing read", last Assumption – REST has been chosen (Clarifications "Plan research decisions"), but several requirements still read as if both channels were open: "with StartCLI, subject to the client check", `CLI_UNAVAILABLE`, "a missing StartCLI installation", and the accepted StartCLI export trace. A tasks author may write tests for paths that cannot occur. – Add one sentence to FR-001a: "Decided: REST (research D-1). Clauses marked 'with StartCLI' apply only if a later change adds that channel." Then rephrase the last Assumption to match the "Export trace in INUBIT" edge case.
- [minor] FR-001 vs research D-1 – FR-001 offers the REST tool "on every node"; research offers it "where `INVENTORY` is possibly capable". – Pick one and use the same wording in both.
- [minor] Edge case "Partner without `Id`" – This edge case says "the first configured field that is present on both sides"; FR-013 says "first configured non-masked partner field". – Add "non-masked" to the edge case.
- [minor] Story 2 scenario 1 – The order says "communication cloud" without saying how clouds are sorted. – Say "communication cloud module name" or "communication cloud in export order".
- [minor] FR-012b vs research D-5 – The spec says the key is created "when the server process starts"; the plan creates it "once per process, on first use". – Either change the spec to "created once per server process, in memory" or align the plan.
